# ADR 010: 한국어 전문검색 — 애플리케이션 단 토큰화 + simple tsvector

> **Date:** 2026-10-27
> **Status:** Accepted · **구현 완료 2026-10-30**

---

## 배경

현재 검색은 pgvector 코사인(벡터) **단일 채널**이다. 하이브리드 검색을 구성하려면
키워드 채널이 필요한데, **PostgreSQL 기본 FTS는 한국어 형태소 분석을 지원하지 않는다.**

## 선택지

| 후보 | 판정 | 사유 |
|---|---|---|
| **앱단 형태소 토큰화 → `simple` tsvector + GIN** | **채택** | 아래 |
| `pg_trgm` | **보조 채널로만** | 3-gram. 한글 2글자 이하 질의는 인덱스 미사용. 조사 결합·어미 변화에 취약. `similarity()`는 의미적 랭킹이 아님 |
| `pg_bigm` | 탈락 | 소스 빌드 → **이미지 재빌드 + `shared_preload_libraries` 변경 + 재기동** 필요. **LIKE 연산자 전용**이라 하이브리드 결합에 쓸 점수가 `bigm_similarity` 하나뿐 |
| `PGroonga` | 탈락 | 동일한 이미지 재빌드 비용. 형태소 토크나이저 기본 사전이 일본어용이라 **한국어 품질 이점이 불확실**. 과거 문서의 크래시 세이프 이슈 |
| OpenSearch + Nori | 탈락 | [ADR-003](003_VectorDB_Strategy.md) 기조와 동일. 상시 클러스터 1식 + PG↔ES 동기화(이중 진실원천) |

## 결정

**Kiwi(앱단)로 토큰화한 결과를 `simple` 설정 tsvector에 넣고 GIN 인덱스를 건다.**

근거:

1. **DB 확장 설치가 불필요하다** — 컨테이너 이미지 재빌드·설정 변경·재기동이 전부 사라진다.
   pg_bigm·PGroonga는 모두 이것이 전제다.
2. `ts_rank_cd` 랭킹과 `tsquery`의 AND/OR/구문검색을 그대로 쓸 수 있다.
3. 이 규모에서 선택 기준은 속도가 아니라 **운영 리스크와 랭킹 품질**이며, 두 축 모두 유리하다.
4. 형태소 분석기를 교체해도 **DB 스키마는 불변, 재색인만** 하면 된다.
5. 질의·문서에 **동일 토크나이저**를 쓰므로 "조사가 분리되지 않는다"는 한국어 고질 문제가
   설계 단계에서 제거된다. n-gram 계열은 이를 확률적으로 우회할 뿐이다.

### 구현 시 반드시 지킬 것

> `array_to_tsvector(tokens)`를 쓰면 **위치 정보가 없어 `ts_rank`/`ts_rank_cd`를 쓸 수 없고
> 소문자 정규화도 되지 않는다.**
> 반드시 `to_tsvector('simple', array_to_string(tokens, ' '))` 형태로 생성한다.

- 필드 가중치는 `setweight`로 제목 A / 키워드 B / 설명 C.
- `tokenizer_ver` 컬럼을 두고 **기동 시 버전 일치를 검증**한다.
  질의·문서 분석기가 불일치하면 **조용히 리콜이 0**이 되므로, 불일치 시 기동 실패시킨다.
- `to_tsquery`에 사용자 입력을 직접 넣지 않는다. **토큰 화이트리스트 기반으로 조립**한다.

### 결합: RRF

벡터 채널과 키워드 채널은 **Reciprocal Rank Fusion**으로 결합하고, **SQL 단일 CTE**로 구현한다.
점수 정규화 가중합은 채널별 분포 통계가 필요한데 현 규모에서는 통계가 신뢰할 수 없다.
`k`는 통상 60이 기본값이나 후보군이 작아 과도하게 평탄화될 수 있으므로
`k ∈ {10,20,30,60}` 스윕을 평가 항목에 포함한다.

## 형태소 분석기

**Kiwi (`kiwipiepy`)** 를 사용한다. ⚠️ **0.24.0부터 Apache-2.0, 0.23.2 이하는 LGPL — 버전 고정 필수.**
모델 파일을 패키지에 동봉하므로 런타임 외부 다운로드가 없어 폐쇄망에 유리하다.

## 구현 (2026-10-30)

이 ADR대로 구현했다. 결정과 **달라진 점 두 가지**를 먼저 적는다.

### 어긋난 점 1 — `setweight` 필드 가중치를 넣지 않았다

위에서 "제목 A / 키워드 B / 설명 C"로 정했으나, 색인을 **원본 테이블이 아니라
청크 테이블(`*_vec`)에 붙였기 때문에** 적용할 수 없었다. 청크는 문장 단위로
잘린 조각이라 필드 정체성이 없다 — 어떤 청크가 제목에서 왔는지 저장돼 있지 않다.

청크 테이블을 고른 이유는 세 가지다.

1. `embed_text`는 `chunker`가 **저작권 고지·구분선 같은 정형 문구를 이미 걷어낸**
   텍스트다. 같은 텍스트를 쓰면 키워드 채널이 그 정제를 그대로 물려받는다.
   원본 `content`를 쓰면 모든 기사에 붙는 `저작권자 ⓒ…`가 색인에 들어간다.
2. 두 채널이 **같은 단위로 랭크돼야** RRF 결합이 성립한다. 한쪽은 문서, 다른 쪽은
   청크 최대값이면 순위의 의미가 달라진다.
3. `sync.py`가 청크를 쓰는 **유일한 자리**다. 여기서 같이 만들면 "벡터는 새
   텍스트인데 토큰은 옛 텍스트"인 상태가 생길 수 없다. 그 상태는 오류 없이 성립한다.

필드 가중치는 청크에 출처 필드를 기록하면 되살릴 수 있다. 지금은 넣지 않았다 —
`ts_rank_cd`의 cover density가 "질의어를 더 많이, 더 가깝게 담은 청크"를 위로
올리고 있어 최소선에서는 이것으로 충분하다고 봤다. **목표선 항목으로 남긴다.**

### 어긋난 점 2 — 1글자 토큰을 버리지 않는다

처음에는 변별력이 없다고 보고 걸렀는데, 실제로는 핵심 의미가 1글자 조각에
실려 가는 경우가 많았다.

    `대역폭`   → 대역 + **폭**      (폭을 버리면 '주파수 대역' 기사와 구분 불가)
    `전기차`   → 전기 + **차**      (차를 버리면 전기 일반 기사와 구분 불가)
    `맨몸으로` → 맨(XPN) + **몸**   (몸을 버리면 토큰이 **하나도 안 남는다**)

정작 변별력 없는 1글자(`것`·`수`·`때`·`등`)는 의존명사(NNB)라 품사 단계에서
이미 빠진다. 고빈도 토큰 처리는 길이가 아니라 문서빈도로 할 일이다.

### 만든 것

| 구성요소 | 내용 |
|---|---|
| [src/search/tokenize.py](../../src/search/tokenize.py) | Kiwi 토큰화. 내용어(NNG·NNP·VV·VA·XR·SL·SH·SN)만 남기고 조사·어미·기호 제거 |
| [src/search/hybrid.py](../../src/search/hybrid.py) | 두 채널 + RRF를 **SQL 단일 CTE**로. `rrf_k` 조정 가능 |
| [sql/migration_2026_10_30_keyword_channel.sql](../../sql/migration_2026_10_30_keyword_channel.sql) | `*_vec` 4종에 `token_text`·`tokenizer_ver`·`tsv`(생성 컬럼) + GIN |
| [scripts/backfill_tokens.py](../../scripts/backfill_tokens.py) | 기존 청크 163,407건 토큰 채우기. 중단·재개 가능 |
| [scripts/search_demo.py](../../scripts/search_demo.py) | `--mode hybrid`(기본) / `--mode vector`(비교용) / `--why`(근거) |

지킨 것:

- `to_tsvector('simple', array_to_string(...))` 형태를 썼다. `array_to_tsvector`는
  쓰지 않았다 — 위치 정보가 없어 `ts_rank_cd`를 못 쓴다.
- `tsv`는 **생성 컬럼**이다. `token_text`에서 자동 파생되므로 둘이 어긋날 수 없다.
- `tokenizer_ver`에 **분석기·모델·품사 화이트리스트 셋 다** 넣는다
  (`kiwi-0.24.1+model-0.24.0+pos1`). 화이트리스트를 빼면 "같은 kiwipiepy인데
  색인만 조용히 어긋난" 상태를 잡을 수 없다. 검색 진입점에서 대조하고 불일치 시
  `TokenizerMismatch`로 중단시킨다.
- 사용자 입력을 `to_tsquery`에 직접 넣지 않는다. 토큰화를 거치면 화이트리스트가
  자연히 성립한다 — 색인 쪽과 **같은 함수**를 쓰는 것이 질의·문서 토큰 일치의 보장이다.
- `kiwipiepy>=0.24.0` (Apache-2.0). 하한을 내리면 LGPL 구간이다.

### 측정에서 드러난 한계 (2026-10-30)

ADR-018 질의 19건을 전체 코퍼스에서 벡터 단독과 비교했다
([database/hybrid_search.md §6](../database/hybrid_search.md)). 두 가지가 나왔다.

1. **키워드 채널이 리콜을 넓히지 않는다.** top-10에 벡터 top-200 밖 문서가
   올라온 적이 **0건**이다. 재정렬만 한다.
2. **질의 1건에서 명백히 나빠졌다.** `"메모리 대역폭을 늘리는 적층 기술"`에서
   벡터가 2·3위로 올린 HBM 정답 기사가 전부 밀려나고 무관한 반도체 일반
   기사가 올라왔다.

원인은 구조적이다 — **`ts_rank_cd`는 IDF를 쓰지 않는다.** cover density는
질의어가 얼마나 몰려 있는지를 볼 뿐, 그 단어가 얼마나 드문지는 보지 않는다.
OR 질의에서 고빈도어(`기술`·`메모리`)가 빽빽한 문서가 희귀어 `적층`(df 23)을
담은 정답을 밀어낸다.

형태소 분해가 이 면에서는 **손해를 보기도 한다**. `전기차`는 어절로는 드물지만
`전기`+`차`로 쪼개면 둘 다 흔하다. ADR-018의 최희귀어 부재 규칙 적중이
4/8 → 2/7로 떨어진 것이 그 결과다. 조사 분리의 이득(문서빈도 65배 왜곡 제거)이
복합어 분해의 손해보다 큰지는 **평가셋 없이 판정할 수 없다.**

처방 후보는 질의 토큰 df 가중 / 고빈도 토큰 제거 / AND 우선 후 OR 폴백이다.
**19건으로 고르지 않는다** — ADR-018이 보인 함정이 정확히 그것이다.

### 남은 것

- **정답지가 없다.** ADR-018의 19건 질의는 "답이 있는가"의 불리언일 뿐 순위
  정답지가 아니라 Recall@k를 만들 수 없다. ADR-018이 경고한 대로 이 크기의
  평가셋으로 얻은 분리는 신뢰할 수 없다 — 품질 수치는 평가셋 확보 후에 낸다.
- `k ∈ {10,20,30,60}` 스윕 — 정답지가 있어야 의미가 있어 같이 미뤘다. 기본값 60.
- 동의어 사전, 필드 가중치, 재순위(cross-encoder).
