# ADR 012: 관계 그래프 저장 — PostgreSQL + NetworkX 하이브리드

> **Date:** 2026-10-27
> **Status:** Accepted

---

## 배경

연구개발계획서 1차년도 "데이터 패턴 모델링 기반 관계 분석", 2차년도 "액티브 메타데이터 기반
네트워크 생성 및 분석 모듈(모비젠)" 과업을 구현하려면 관계(엣지)를 저장·조회·분석해야 한다.

예상 규모: 노드 — 데이터셋 수십 개, 아이템 수만 건 / 엣지 — 수백~수십만 건.

## 결정

**관계는 PostgreSQL에 정규화 저장하고, 전역 그래프 연산은 분석 시점에 NetworkX로 수행한다.**
그래프 데이터베이스(Neo4j/Memgraph)는 도입하지 않는다.

### 저장 설계

- 이종 노드(dataset/item/keyword)를 **(node_type, node_id) 복합 식별자**로 단일 테이블에 담는다.
- 무방향 엣지는 **단방향 1행만 저장**하고, `CHECK` 제약으로 사전순 정규화를 강제한다.
  조회는 전부 전개 뷰(`UNION ALL`)만 본다.
  → 양방향 중복 저장은 **한쪽만 갱신되는 버그가 반드시 발생**한다. 조회 비용은 이 규모에서 논점이 아니다.
- `origin` + `method` + `method_version`을 UNIQUE 키에 포함해
  **규칙 기반 엣지와 외부 모델 기반 엣지가 같은 쌍에 공존**할 수 있게 한다(서로 다른 주장이므로).

### 다중 홉 탐색 — 재귀 CTE 방어 4종 (전부 적용)

1. 깊이 상한을 **재귀항 안에** 둔다 (최종 WHERE에 두면 전개는 다 하고 버린다)
2. **누적 가중치 곱셈 감쇠 컷** — 실질적으로 폭발을 잡는 것은 이것이다
3. 약한 엣지 선차단
4. `CYCLE ... SET ... USING path` — 유사도 그래프는 사이클 투성이이고,
   `depth` 컬럼이 들어가는 순간 `UNION` 중복 제거는 무효가 된다(공식 문서가 명시하는 함정)

### 분석

**PostgreSQL이 진실원천, NetworkX는 일회성 연산 엔진**이다.
엣지 적재 → 지표 계산 → `dcat_graph_metric` 기록 → 그래프 객체 폐기.
상태를 NetworkX에 두지 않으므로 동시성·복구 문제가 없다.

- python-igraph 대신 **NetworkX**를 쓴다. 이 규모에서 성능 차이는 체감되지 않고,
  **순수 Python 의존성(C 확장 없음)** 이 온프레미스 이미지 빌드에서 더 큰 실무 가치를 갖는다.
- Louvain은 **`seed` 고정 필수** — 시드마다 결과가 달라진다.
- 동일 쌍에 여러 relation_type이 있을 때 **가중치 합성 규칙(max)을 명시·문서화**한다.
  합산하면 관계 종류가 많은 쌍이 과대평가된다.
- 지표는 `dcat_graph_metric`에 **run 단위 누적 기록**한다(덮어쓰지 않음) → 시점별 변화 제시 가능.
  `dcat_dataset` 본체에는 컬럼을 추가하지 않는다 — 파생값이 원천 카탈로그를 오염시키면 안 된다.

## 과제 문서용 근거

> 본 과제의 관계 그래프는 생성되는 엣지 수가 수십만 건 이하이다. 이 규모에서는 관계형
> 데이터베이스의 인덱스 탐색과 재귀 CTE만으로 다중 홉 탐색 성능이 충분히 확보되며, 별도
> 그래프 데이터베이스 도입 시 발생하는 이중 적재 파이프라인·동기화 지연·운영 부담이 성능
> 이득을 상회한다. 또한 관계 정보를 메타데이터 카탈로그(DCAT)와 동일한 PostgreSQL 인스턴스에
> 보관함으로써 참조 무결성을 외래키 제약으로 직접 보장할 수 있다.

## 재검토 조건

- 엣지 **100만 건**을 상회할 때
- **실시간 가변 길이 경로 질의**가 상시 워크로드가 될 때

(NetworkX 한계: ~10만 엣지는 전 지표 수 초. ~100만에서 betweenness는 O(V·E)로 사실상 불가.)
