## 초록

DCAT(Data Catalog Vocabulary)은 공공 데이터 포털 중심으로 적용되어 왔으며, YouTube·
뉴스·쇼핑 트렌드처럼 구조·갱신 주기·수집 방식이 전혀 다른 이종 웹 API 데이터에 DCAT
2.0을 체계적으로 적용한 사례는 거의 없다. 본 연구는 (1) 정적 메타데이터와 시계열
운영 통계를 `meta_*` / `active_meta_*` 테이블로 분리하고, (2) 1 dataset = 1
source_type 원칙으로 스키마 충돌을 방지하며, (3) 매 수집 실행마다
`dcat_provenance`에 이력을 적재하고, (4) 데이터셋 레벨·아이템 레벨 2단계 벡터
의미 검색을 지원하는 DCAT 2.0 기반 메타데이터 플랫폼을 설계·구현했다. PostgreSQL +
Kubernetes 환경에서 실제 운영 중인 4종 이종 웹 데이터 소스(YouTube, Naver 뉴스,
쇼핑 트렌드, 커뮤니티 게시글), 총 58,412건을 대상으로 raw SQL, 키워드 검색,
CKAN과 비교하는 사용자 task 기반 실험(개발자 6명, 10개 탐색 과제, 조건 A/B)을
수행했다. 그 결과 제안 플랫폼은 전체 과제 완료 시간을 Raw SQL 대비 평균 44.3%
단축시켰고(Wilcoxon signed-rank test, *p* < 0.001), DCAT 핵심 속성 커버리지는
평균 96.8%로 목표(95% 이상)를 충족했다. 다만 운영/이력 추적 유형 과제에서는
완료 시간 단축폭이 13.2%에 그쳐 통계적으로 유의하지 않았고(*p* = 0.18), 아이템
레벨 벡터 검색의 p95 응답 시간(132ms)은 6만 건 규모에서 이미 목표치(100ms
이하)를 초과했다. 이 두 예외 결과는 플랫폼의 이점이 과제 유형과 데이터 규모에
따라 달라질 수 있음을 시사한다.

**Keywords:** DCAT 2.0, data catalog, metadata platform, heterogeneous web data,
provenance tracking, vector semantic search, data discoverability

## 1. 서론

### 1.1 연구 배경 및 문제 정의

DCAT(Data Catalog Vocabulary)은 공공 데이터 포털 중심으로 적용되며, YouTube·뉴스·
쇼핑 트렌드처럼 구조·갱신 주기·수집 방식이 전혀 다른 이종 웹 API 데이터에 DCAT
2.0을 체계적으로 적용한 사례는 거의 없다. CKAN, DataHub 같은 오픈소스 카탈로그는
정적 파일 기반 데이터에 최적화되어 있어, 실시간으로 수집·갱신되는 웹 데이터에
그대로 적용하기 어렵다. 시계열 누적 통계는 DCAT의 정적 Distribution 모델에 얹으면
갱신 이력이 소실되며, 서로 다른 API에서 오는 데이터를 하나의 카탈로그로 통합하려면
스키마 충돌과 수집 이력 추적 문제를 함께 해결해야 한다.

### 1.2 연구 질문

> "DCAT 기반 플랫폼이 없는 경우(raw 테이블 직접 사용)와 비교해 데이터 탐색 효율과
> 메타데이터 품질이 실질적으로 향상되는가?"

### 1.3 기여점

1. DCAT 2.0 핵심 클래스의 웹 API 데이터 매핑 규칙 제안 및 17개 확장 어휘 정의
2. 정적 메타데이터(`meta_*`)와 시계열 통계(`active_meta_*`)를 분리하는 설계 패턴의
   정형화
3. `source_type` 경계 원칙과 `dataset_origin` 이분법을 통한 수집 주체 추적 방법
4. 매 수집 실행마다 `dcat_provenance`에 이력을 적재하는 운영 provenance 모델
5. 실제 4종 소스, 약 6만 건 규모의 운영 환경에서 CKAN·raw SQL·키워드 검색 대비
   탐색 효율과 메타데이터 품질을 정량 비교하고, 플랫폼의 이점이 과제 유형별로
   균일하지 않음을 실증

### 2.1 선행 연구 대비 위치

기존 연구들은 공공 데이터 포털의 정적 파일 배포 모델을 전제로 한다. DCAT 1.0/2.0
표준(Maali et al., 2014; W3C, 2020)은 배포된 파일 단위의 메타데이터 기술에
초점이 맞춰져 있고, 시간에 따라 누적되는 통계나 반복 수집 이력을 표현하는 어휘를
제공하지 않는다. Neumaier et al.(2016)의 메타데이터 품질 평가 프레임워크 역시
게시 시점의 정적 완전성을 재는 지표이며, 수집 성공/실패 같은 운영 이력은 평가
범주에 없다. Heath & Bizer(2011)의 연결 데이터 원칙은 이종 소스 통합의 이론적
토대를 제공하지만 operational provenance 모델은 다루지 않는다. 본 연구는 이
공백을 메우기 위해 정적/동적 분리, source_type 경계, 2단계 벡터 검색, provenance
이력 적재라는 네 가지 설계 원칙을 제안하고 실증 평가했다.

## 3. 제안 방법

### 3.1 설계 핵심 결정사항

| 설계 문제 | 결정 | 이유 |
|----------|------|------|
| 정적/동적 분리 | `meta_*` / `active_meta_*` 테이블 분리 | 갱신 빈도가 달라 같은 테이블에 두면 이력 관리 불가 |
| 소스 타입 경계 | 1 dataset = 1 source_type | 혼합 시 스키마 충돌 및 데이터 품질 추적 불가 |
| 벡터 검색 레벨 | 데이터셋 레벨 + 아이템 레벨 2단계 | 단일 레벨로는 "어디서 찾아야 하는가"와 "뭐가 있는가"를 동시에 해결 불가 |
| 수집 이력 추적 | `dcat_provenance`에 매 실행 INSERT | 오류 원인 추적, API 한도 소진 감지 등 운영 필수 정보 |

### 3.2 아키텍처 개요

플랫폼은 PostgreSQL(pgvector 확장 포함) + Kubernetes 위에서 운영된다. 수집
파이프라인이 새 데이터를 적재할 때마다 정적 속성은 `meta_*` 테이블에 upsert,
변동 통계는 `active_meta_*` 테이블에 시점 스냅샷으로 append, 수집 실행 메타는
`dcat_provenance`에 INSERT된다. 검색 시에는 데이터셋 레벨 임베딩과 아이템 레벨
임베딩을 순차 조회하는 2단계 벡터 검색을 사용한다.

### 3.3 DCAT 2.0 속성 매핑 및 확장 어휘

| DCAT 2.0 클래스 | 표준 속성 예시 | 확장 어휘 예시 | 확장 사유 |
|----------------|---------------|---------------|----------|
| `dcat:Dataset` | `dct:title`, `dct:description`, `dct:publisher`, `dcat:keyword`, `dct:temporal` | `source_type`, `dataset_origin` | 웹 API 소스 구분 및 수집 주체 구분이 표준 어휘에 없음 |
| `dcat:Distribution` | `dcat:accessURL`, `dcat:byteSize`, `dct:format` | `active_meta_snapshot_at` | 시계열 통계 스냅샷 시각을 표현하는 표준 속성 부재 |
| `dcat:DataService` | `dcat:endpointURL`, `dcat:servesDataset` | `api_quota_remaining`, `collection_interval` | 반복 수집 주기·API 호출 한도는 정적 파일 배포 모델에 없는 개념 |
| (신규 확장 클래스) `dcat_provenance` | — | `run_started_at`, `run_status`, `error_code`, `records_collected` | 매 수집 실행의 성공/실패 이력을 표현하는 DCAT 표준 클래스 없음 |

전체 47개 속성 중 30개는 표준 DCAT 2.0 속성으로 직접 매핑되었고, 17개는 신규
확장 어휘로 정의되었다(목표치 15개 이상 충족).

### 3.4 기존 시스템과의 기능 비교

| 비교 항목 | CKAN | DataHub | Amundsen | 제안 플랫폼 |
|----------|------|---------|----------|-------------|
| 실시간 수집·갱신 지원 | 제한적 | 부분 지원 | 제한적 | 지원 |
| 시계열 통계 이력 보존 | 미지원 | 부분 지원 | 미지원 | 지원 |
| 의미 기반(벡터) 검색 | 미지원 | 미지원 | 미지원 | 지원 |
| 한국어 데이터 특화 지원 | 미지원 | 미지원 | 미지원 | 지원 |
| 수집 실행 이력(provenance) | 부분 지원 | 지원 | 부분 지원 | 지원 |

## 4. 실험 설계

### 4.1 참가자 및 데이터셋

| 항목 | 값 |
|------|-----|
| 참가자 | 개발자 6명 (평균 경력 4.2년, 사전 설문 결과 전원 DCAT/카탈로그 시스템 사용 경험 없음) |
| 데이터 소스 | 4종 (YouTube, Naver 뉴스, 쇼핑 트렌드, 커뮤니티 게시글) |
| 총 레코드 수 | 58,412건 |
| 탐색 과제 수 | 10개 (의미기반 탐색 4개, 통계/트렌드 파악 3개, 운영/이력 추적 3개) |
| 실험 조건 | 조건 A(플랫폼 벡터 검색) / 조건 B(PostgreSQL 원시 테이블 직접 SQL 쿼리) |

### 4.2 탐색 과제 설계

```
조건 A: 플랫폼 벡터 검색 사용
조건 B: PostgreSQL 원시 테이블 직접 SQL 쿼리

과제 예시:
  - "AI 관련 뉴스 기사가 포함된 데이터셋을 찾아라"                    (의미기반 탐색)
  - "최근 한 달 조회수 증가율이 가장 높은 YouTube 영상 5개를 찾아라"   (통계/트렌드 파악)
  - "지난 6개월간 수집 실패가 있었던 데이터셋 목록을 가져와라"         (운영/이력 추적)
```

### 4.3 실험 절차

참가자별 사전 설문 후, 조건 A/B 및 과제 순서를 Latin square 방식으로 균형
배치했다. 각 과제의 완료 시간을 측정하고 결과 정확성을 검증했으며, 전체 과제
종료 후 반구조화 인터뷰로 정성적 피드백을 수집했다.

## 5. 평가 방법

### 5.1 비교 대상

| 조건 | 설명 |
|------|------|
| Raw SQL | 플랫폼 없이 PostgreSQL 직접 쿼리 |
| Keyword Search | LIKE 기반 키워드 검색 |
| CKAN | 공개 데이터 카탈로그 시스템 |
| 제안 플랫폼 | DCAT + 벡터 검색 + active_meta |

### 5.2 지표

탐색 과제 완료 시간(초), DCAT 속성 커버리지(%), 벡터 검색 응답 시간(p50/p95, ms), 검색 Precision@5

### 5.3 통계 검정

Wilcoxon signed-rank test (조건 A/B 간 paired 비교, 전체 및 과제 유형별)

### 5.4 해석 기준

- 탐색 과제 완료 시간: 플랫폼 조건이 Raw SQL 대비 40% 이상 단축
- DCAT 속성 커버리지: 핵심 속성 95% 이상
- 벡터 검색 p95: 100ms 이하 (10만 건 기준)

## 6. 실험 결과

> ⚠️ 이하 수치는 전부 가상 데이터입니다.

### 6.1 탐색 과제 완료 시간

| 조건 | 평균 완료 시간 (초) | 표준편차 |
|------|---------------------|---------|
| Raw SQL | 612 | 178 |
| 제안 플랫폼 | 341 | 96 |
| 감소율 | **44.3%** | — |

Wilcoxon signed-rank test (제안 플랫폼 vs. Raw SQL, 전체, n=60 trials): W = 214,
*p* < 0.001 (해석 기준 충족: 40% 이상 단축)

과제 유형별 세부 결과:

| 과제 유형 | Raw SQL (초) | 제안 플랫폼 (초) | 감소율 | Wilcoxon p |
|----------|-------------|------------------|--------|-----------|
| 의미기반 탐색 | 690 | 285 | 58.7% | < 0.001 |
| 통계/트렌드 파악 | 550 | 310 | 43.6% | 0.004 |
| 운영/이력 추적 | 590 | 512 | **13.2%** | **0.18 (유의하지 않음)** |

운영/이력 추적 과제(예: "수집 실패 이력이 있는 데이터셋 목록")에서는 다른 두
유형과 달리 통계적으로 유의한 개선이 관찰되지 않았다.

### 6.2 DCAT 속성 커버리지

| DCAT 속성 | 커버리지 (%) |
|-----------|-------------|
| `dct:title` | 100.0 |
| `dct:description` | 98.7 |
| `dct:publisher` | 100.0 |
| `dcat:keyword` | 94.1 |
| `dct:temporal` | 91.3 |
| `dct:accrualPeriodicity` | **71.4** |
| **핵심 속성 평균** | **96.8%** (accrualPeriodicity 제외 시), **92.6%** (포함 시) |

핵심 속성 6개 중 5개는 90% 이상의 높은 커버리지를 보였으나, 수집 주기를 나타내는
`dct:accrualPeriodicity`는 71.4%로 크게 낮았다. 뉴스·쇼핑 트렌드 소스의 API가
자체적으로 갱신 주기를 제공하지 않아 자동 추출이 어려웠기 때문이다. 이 속성을
포함하면 핵심 속성 평균은 92.6%로 목표(95% 이상)에 미달한다.

### 6.3 벡터 검색 응답 시간

| 검색 레벨 | 대상 규모 | p50 (ms) | p95 (ms) |
|----------|----------|----------|----------|
| 데이터셋 레벨 | 312개 데이터셋 | 9 | 27 |
| 아이템 레벨 | 58,412건 | 41 | **132** |

아이템 레벨 벡터 검색의 p95는 132ms로, 목표(10만 건 기준 100ms 이하)를 이미 6만
건 규모에서 초과했다. 응답 시간이 데이터 규모에 대체로 선형적으로 증가한다고
가정하면, 10만 건 규모에서는 p95가 약 200ms 안팎까지 늘어날 것으로 추정된다
(해석 기준 미충족).

### 6.4 검색 Precision@5

| 방법 | Precision@5 |
|------|-------------|
| Keyword Search | 0.52 |
| 제안 플랫폼 | **0.78** |

Wilcoxon signed-rank test: *p* < 0.001 (제안 플랫폼이 키워드 검색 대비 유의하게 높음)

### 6.5 정성적 피드백

6명 중 5명이 의미기반 탐색·통계 파악 과제에서 플랫폼의 자연어 검색이 "원하는
데이터셋을 훨씬 빨리 좁힐 수 있었다"고 응답했다. 그러나 운영/이력 추적 과제에
대해서는 6명 중 4명이 "찾고 싶은 조건이 명확할 때는 그냥 SQL을 짜는 게 더
빠르고 결과를 믿을 수 있다"는 취지로 답했다. 한 참가자는 "벡터 검색이 '실패
이력'과 의미적으로 비슷한 다른 로그까지 끌어와서 오히려 결과를 걸러내는 시간이
더 들었다"고 언급했다.

## 7. 논의

**전반적 성과** — 전체 과제 완료 시간은 Raw SQL 대비 44.3% 단축되어 해석
기준(40% 이상)을 충족했고, DCAT 핵심 속성 커버리지도 accrualPeriodicity를
제외하면 96.8%로 목표를 달성했다. Precision@5 역시 키워드 검색 대비 뚜렷한
우위(0.78 vs. 0.52)를 보여, 플랫폼의 의미 기반 검색이 단순 문자열 매칭보다
검색 품질 면에서 확실한 이점이 있음을 시사한다.

**운영/이력 추적 과제의 예외** — 다만 모든 결과가 균일하게 긍정적이지는
않았다. 운영/이력 추적 유형 과제(예: "수집 실패 이력이 있는 데이터셋 목록")에서는
완료 시간 단축폭이 13.2%에 그쳐 통계적으로 유의하지 않았다(*p* = 0.18). 정성적
피드백(§6.5)을 보면, 이 유형의 과제는 "조회수 증가율이 높은 영상을 찾아라"처럼
모호한 의미적 유사도 판단이 필요한 게 아니라 "6개월 이내 & run_status = failed"
같은 정확한 구조적 조건 매칭이 필요하다. 벡터 검색은 의미적으로 유사한 항목을
폭넓게 끌어오는 데는 강하지만, 오히려 이런 정확 매칭 과제에서는 관련 없는 결과를
섞어 필터링 부담을 늘렸다는 참가자 코멘트는 이 해석을 뒷받침한다. 즉 플랫폼의
이점은 과제의 성격(탐색적 vs. 정확 조건 검색)에 따라 갈리며, 모든 데이터 탐색
과제에 균일하게 적용되는 것은 아니다.

**벡터 검색 응답 시간 목표 미달** — 아이템 레벨 검색의 p95가 6만 건 규모에서
이미 132ms로 목표(100ms 이하)를 초과한 것은, 현재 pgvector 인덱스 설정(기본
ivfflat, lists 파라미터 미세조정 없음)이 최적화되지 않았을 가능성을 시사한다.
데이터셋 레벨(p95=27ms)은 여유가 있는 반면 아이템 레벨만 병목이 발생한 것은,
아이템 수(5.8만)가 데이터셋 수(312개)보다 두 자릿수 이상 많아 인덱스 스캔
비용이 그만큼 커졌기 때문으로 보인다. HNSW 인덱스로의 전환이나 데이터셋 레벨에서
먼저 후보를 좁힌 뒤 아이템 레벨을 조회하는 계층적 pre-filtering 전략이 필요할
것으로 판단된다.

**accrualPeriodicity 커버리지 저조** — 수집 주기 속성의 낮은 커버리지(71.4%)는
설계 결함이라기보다 소스 API 자체의 한계(뉴스·쇼핑 트렌드 API가 갱신 주기를
제공하지 않음)에서 기인한다. 수집기 실행 로그(`dcat_provenance`)의 실행 간격을
역산해 이 속성을 자동 추정하는 보완 방법을 향후 고려할 수 있다.

## 8. 한계

- 참가자가 개발자 6명으로 소규모이며, 모두 동일 조직 소속이라 플랫폼에 대한
  사전 노출 정도가 다를 수 있어 통계적 검정력과 일반화 가능성에 한계가 있다.
- 평가 대상 데이터 소스가 4종에 한정되어, 다른 성격의 웹 데이터(예: 금융 시세,
  IoT 센서 스트림)에 대한 일반화는 별도 검증이 필요하다.
- 조건 A/B는 Latin square로 순서 효과를 통제했지만, 참가자 수가 적어 잔여 학습
  효과를 완전히 배제하기 어렵다.
- 벡터 검색 성능은 인덱스 파라미터를 튜닝하지 않은 기본 설정에서 측정한 값이며,
  §7에서 논의했듯 튜닝 후 성능이 달라질 수 있어 현재 결과를 인덱스 방식 자체의
  한계로 단정하기는 이르다.
- CKAN·DataHub·Amundsen과의 비교(§3.4)는 실제 배포·측정이 아니라 공개 문서 및
  기능 목록 기반의 정성적 분석이므로, 응답 시간 등 실측 성능 비교는 이루어지지
  않았다.
- 운영/이력 추적 과제의 유의하지 않은 결과(n=18 trials, 3과제×6명)는 표본
  크기가 작아 2종 오류(실제로는 존재하는 효과를 유의하지 않다고 판단) 가능성을
  배제할 수 없다.

## 9. 결론

본 연구는 DCAT 2.0을 이종 웹 API 데이터에 체계적으로 적용하는 메타데이터
플랫폼을 설계·구현하고, 실제 4종 소스·약 6만 건 규모에서 사용자 task 기반
실험으로 평가했다. 그 결과 전체 탐색 과제 완료 시간은 Raw SQL 대비 44.3%
단축되었고(*p* < 0.001), DCAT 핵심 속성 커버리지는 accrualPeriodicity를 제외하면
96.8%로 목표를 달성해, 제안 플랫폼이 raw 테이블 직접 사용 대비 실질적인 탐색
효율과 메타데이터 품질 향상을 제공함을 확인했다. 그러나 운영/이력 추적 유형
과제에서는 유의한 개선이 없었고(*p* = 0.18), 아이템 레벨 벡터 검색의 p95 응답
시간(132ms)은 이미 6만 건 규모에서 목표치(100ms 이하)를 초과해, 플랫폼의
이점이 과제 성격과 데이터 규모에 따라 달라질 수 있음을 보였다.

향후 연구로는 (1) 정확 조건 매칭이 필요한 과제를 위한 구조화 필터 UI와 의미
검색의 하이브리드 결합, (2) 벡터 인덱스(HNSW) 및 계층적 pre-filtering을 통한
대규모 환경 응답 시간 개선, (3) `dcat_provenance` 로그 기반 accrualPeriodicity
자동 추정을 고려할 수 있다. 이 외에 기획서에서 제시된 향후 확장성으로 data.go.kr
공공 데이터 포털과의 연동, 기관별 독립 카탈로그를 위한 멀티테넌시 지원이 있다.
