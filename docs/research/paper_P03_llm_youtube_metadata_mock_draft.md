## 초록

YouTube 영상의 API 메타데이터(제목·설명·태그)는 업로더 입력값으로 키워드 스터핑이나
콘텐츠 내용과의 불일치가 빈번하다. 자동 자막(STT) 트랜스크립트가 있지만 한국어 STT는
전문 용어 오인식이 심해 그대로 쓰기 어렵다. 본 연구는 STT 노이즈가 심한 한국어
트랜스크립트에서 공개 LLM으로 요약·키워드·개체명·콘텐츠 유형 4종의 구조화 메타데이터를
자동 추출하는 파이프라인을 제안한다. 기술 110편, 의료 50편, 뉴스 50편으로 구성된 영상
210편과 검색 평가용 Query-Relevance 쌍 50개로 평가한다. 무료 Groq API 모델
(llama-3.1-8b, gemma2-9b)을 유료 품질 상한 기준(GPT-4o-mini)과 비교한 결과,
gemma2-9b는 인간 평가 3.7/5.0으로 실용 기준(3.5/5.0)을 충족했으나 llama-3.1-8b는
3.4/5.0으로 기준에 미달했다. 개체명 인식 F1은 세 모델 모두 상대적으로 낮았고 특히
의료 도메인(gemma2-9b 기준 0.48)에서 STT 전문 용어 오인식의 영향이 컸다. 그러나 이
낮은 개체명 인식 품질에도 불구하고 검색 성능 향상은 뚜렷했다 — LLM 메타데이터를 모두
추가한 조건에서 NDCG@5가 API 메타데이터 단독 대비 0.078 향상되었으며(paired t-test,
*p* = 0.012), 이 향상의 대부분(0.053/0.078)은 개체명이 아니라 요약·키워드 추가 단계에서
이미 발생했다. 즉 메타데이터 품질 지표(NER F1)와 검색 기여도는 반드시 일치하지
않는다는 점을 실증한다.

**Keywords:** large language models, information extraction, Korean NLP, ASR noise, structured
metadata generation, retrieval augmentation, few-shot prompting, YouTube

## 1. 서론

### 1.1 연구 배경 및 문제 정의

YouTube API 메타데이터(제목·설명·태그)는 업로더 입력값이라는 태생적 한계를 갖는다.
검색 노출을 위한 키워드 스터핑이 흔하고, 실제 콘텐츠 내용과의 불일치도 빈번하다.
자동 자막(STT) 기반 트랜스크립트는 콘텐츠 내용을 더 충실히 반영할 잠재력이 있지만,
한국어 STT는 전문 용어 오인식이 심해 그대로 활용하기 어렵다. 본 연구는 GPU 자원 없이
무료 API만으로 이 노이즈를 다루면서도 검색에 실제로 기여하는 구조화 메타데이터를
뽑아낼 수 있는지를 실증한다.

### 1.2 연구 질문

> LLM이 생성한 메타데이터를 추가했을 때, 트랜스크립트가 없는 API 메타데이터만
> 사용한 경우 대비 검색 정확도가 통계적으로 유의하게 향상되는가?

### 1.3 기여점

1. STT 노이즈 유형 분류 및 전처리 파이프라인 (타임스탬프 제거, 반복 구문 병합,
   토큰 수 기반 청킹)
2. 요약·키워드·개체명·콘텐츠 유형 4종을 동시에 추출하는 구조화 출력 프롬프트 설계
3. 무료 LLM(Groq: llama-3.1-8b, gemma2-9b)의 한국어 실용 성능 측정 — 두 모델 중
   하나만 실용 기준을 충족한다는 점을 실증
4. LLM 메타데이터 추가 시 벡터 검색 품질 향상의 정량화 — 개체명 인식 품질이 낮아도
   검색 기여도는 뚜렷할 수 있음을 실증

### 2.1 선행 연구 대비 위치

GPT-3(Brown et al., 2020)와 Emergent Abilities(Wei et al., 2022)는 모델 규모가
정보 추출 능력에 미치는 영향을 실증했지만 평가는 영어 벤치마크 중심이다. 본 연구
결과(§6.1)는 이 창발 능력이 한국어·9B급 모델(gemma2-9b)에서는 실용 기준을 충족하는
반면 8B급(llama-3.1-8b)에서는 근소하게 미달한다는, 파라미터 수만으로는 예측하기
어려운 경계 지점을 보여준다. Llama 2(Touvron et al., 2023)의 한국어 이해
가능성이나 T5(Raffel et al., 2020)의 text-to-text 통일 프레임워크 역시 구조화
메타데이터 추출의 실용성이나 교착어 STT 노이즈 로버스트성을 직접 검증하지 않았다.
무엇보다 이들 선행 연구는 생성 품질 자체만을 평가할 뿐, 그 메타데이터가 검색
성능으로 이어지는지는 다루지 않는다 — 본 연구는 §6.3에서 이 둘이 반드시 같은
방향으로 움직이지 않음을 실증적으로 보인다.

## 3. 제안 방법

### 3.1 파이프라인 구성

```
[youtube-transcript-api] → 원시 트랜스크립트
        ↓ 전처리
  - 타임스탬프 제거
  - 반복 구문 병합 (STT 버벅임 제거)
  - 토큰 수 계산 → 16K 초과 시 청킹
        ↓ LLM 호출 (Groq API)
  프롬프트: "아래 YouTube 트랜스크립트를 분석하여 JSON으로 반환하라.
             {summary, keywords, entities, content_type}"
        ↓ 파싱 및 검증
  - JSON schema validation
  - 빈 필드 fallback 처리 (title+description으로 재시도)
        ↓
  meta_youtube_video_ai 테이블 저장
```

### 3.2 Long Context 처리 전략

| 트랜스크립트 길이 | 전략 |
|----------------|------|
| ≤ 8K 토큰 | 전체 입력 |
| 8K ~ 32K 토큰 | Map-Reduce: 청크별 요약 → 최종 통합 |
| > 32K 토큰 | 앞·중간·뒤 3구간 샘플링 후 통합 |

### 3.3 구조화 출력 프롬프트

프롬프트는 요약(3문장 내외)·키워드(5~10개)·개체명(인물/기관/제품/기술 용어)·콘텐츠
유형 4개 필드를 하나의 JSON 객체로 동시에 요구한다. 4종을 한 번의 호출로 묶어
요청함으로써 무료 API의 일일 요청 한도(Groq 14,400 req/day) 안에서 영상당 호출
횟수를 최소화한다.

## 4. 실험 설계

### 4.1 데이터셋

| 항목 | 값 |
|------|-----|
| 영상 수 | 210편 (기술 110편 + 의료 50편 + 뉴스 50편) |
| 인간 레퍼런스 | 영상별 3문장 요약, 5~10개 키워드, 개체명 목록 (평가자 2인, 불일치 시 제3자 조정) |
| 검색 평가용 Query-Relevance 쌍 | 50개 |
| 데이터 소스 | `meta_youtube_video`, `youtube-transcript-api` 원시 트랜스크립트 |

### 4.2 조건 비교

```
조건 A: 제목 + 설명 + 태그 (API 메타데이터만)
조건 B: 조건 A + LLM 요약 + 키워드
조건 C: 조건 B + 개체명 + 콘텐츠 유형
```

### 4.3 LLM 비교

```
llama-3.1-8b   (Groq, 무료)
gemma2-9b      (Groq, 무료)
GPT-4o-mini    (유료, 품질 상한 기준)
```

### 4.4 실험 절차

1. 영상 210편의 트랜스크립트 수집·전처리, 인간 레퍼런스 2인 독립 작성 후 불일치 조정.
2. 3개 LLM 각각으로 전체 영상에 대해 요약·키워드·개체명·콘텐츠 유형 생성.
3. LLM별 출력을 인간 레퍼런스와 비교(ROUGE-L, Keyword F1, NER F1) 및 5점 인간 평가.
4. 검색 인덱싱에는 실용 기준을 충족한 gemma2-9b 출력을 사용해 조건 A/B/C를 구성하고
   Query-Relevance 쌍 50개로 NDCG@5/MRR/Recall@10 측정.
5. 3개 LLM에 대해 영상당 평균 API 호출 횟수·응답 시간을 기록.

## 5. 평가 방법

### 5.1 평가 1: 메타데이터 품질

| 지표 | 측정 대상 | 계산 방법 |
|------|----------|---------|
| ROUGE-L | 요약 품질 | LLM 요약 vs. 인간 레퍼런스 요약의 최장 공통 부분 수열 |
| Keyword F1 | 키워드 적중률 | LLM 키워드 ∩ 인간 키워드 / Union |
| NER F1 | 개체명 인식 정확도 | LLM 개체명 vs. 인간 레이블 |
| 인간 평가 (5점) | 전반적 유용성 | 관련성·정확성·완결성 항목 |

### 5.2 평가 2: 검색 품질 향상

```
실험 절차:
1. 조건 A/B/C 각각으로 영상 210편을 임베딩·인덱싱 (gemma2-9b 출력 사용)
2. 50개 검색 쿼리를 각 조건에서 실행
3. 결과 상위 10개와 정답셋(관련 영상 목록) 비교
```

| 지표 | 측정 대상 | 연결 이유 |
|------|----------|----------|
| NDCG@5 | 상위 5개 결과의 순위 품질 | 사용자는 보통 상위 몇 개만 확인 |
| MRR | 첫 번째 관련 결과의 순위 역수 평균 | 정확한 답을 얼마나 빨리 찾는지 |
| Recall@10 | 정답 중 상위 10개 안에 있는 비율 | 놓치는 관련 결과가 없는지 |

### 5.3 통계 검정 및 해석 기준

- **paired t-test** — 쿼리별 NDCG@5 차이(조건 C vs. 조건 A)의 유의성을 검정
  (p < 0.05 기준).
- 해석 기준: NDCG@5 Δ(C−A) ≥ 0.05 (p < 0.05) / llama-3.1-8b 인간 평가 3.5/5.0 이상 /
  영상 1편당 Groq 호출 ≤ 3회, 응답 시간 ≤ 10초

## 6. 결과

> ⚠️ 이하 수치는 전부 가상 데이터입니다.

### 6.1 메타데이터 품질 (LLM별)

| 모델 | ROUGE-L | Keyword F1 | NER F1 | 인간 평가 (5점) |
|------|---------|-----------|--------|----------------|
| llama-3.1-8b (무료) | 0.44 | 0.57 | 0.59 | **3.4** |
| gemma2-9b (무료) | 0.49 | 0.63 | 0.64 | **3.7** |
| GPT-4o-mini (유료, 상한) | 0.61 | 0.74 | 0.81 | 4.4 |

해석 기준(llama-3.1-8b 인간 평가 ≥ 3.5) 충족 여부: **미충족** (3.4/5.0, 기준 대비
−0.1). gemma2-9b는 3.7/5.0으로 **충족**.

### 6.2 도메인별 메타데이터 품질 세부 (gemma2-9b 기준)

| 도메인 | ROUGE-L | Keyword F1 | NER F1 |
|--------|---------|-----------|--------|
| 기술 | 0.53 | 0.68 | 0.71 |
| 의료 | 0.41 | 0.54 | **0.48** |
| 뉴스 | 0.52 | 0.66 | 0.69 |

의료 도메인의 NER F1(0.48)이 다른 두 도메인 대비 뚜렷하게 낮다. 트랜스크립트
검수 결과 약제명·시술명 등 전문 용어의 STT 오인식(예: "보톡스" → "보독스")이
주요 원인으로 관찰되었다.

### 6.3 검색 품질 향상 (조건별, gemma2-9b 메타데이터 사용)

| 조건 | NDCG@5 | MRR | Recall@10 |
|------|--------|-----|-----------|
| A (API 메타데이터만) | 0.598 | 0.531 | 0.688 |
| B (A + 요약 + 키워드) | 0.651 | 0.579 | 0.719 |
| C (B + 개체명 + 콘텐츠 유형) | **0.676** | **0.602** | **0.734** |

Δ(NDCG@5, C − A) = **0.078** / paired t-test: *t* = 2.68, *p* = **0.012**

해석 기준(Δ NDCG@5 ≥ 0.05, p < 0.05) 충족 여부: **충족**

단, 조건별 증분을 분해하면 A→B 구간의 기여(Δ=0.053)가 B→C 구간의 기여(Δ=0.025)
보다 두 배 이상 크다 — 즉 검색 성능 향상의 대부분은 요약·키워드 추가에서 이미
발생했고, NER F1이 상대적으로 낮았던 개체명·콘텐츠 유형(조건 C)의 증분 기여는
작지만 여전히 양(+)의 방향으로 유의하다.

### 6.4 처리 효율

| 모델 | 영상당 평균 API 호출 횟수 | 평균 응답 시간 | 일일 처리 가능 영상 수 (14,400 req/day 기준) |
|------|--------------------------|---------------|----------------------------------------|
| llama-3.1-8b | 2.0회 | 4.3초 | 약 7,200편 |
| gemma2-9b | 2.2회 | 5.1초 | 약 6,545편 |
| GPT-4o-mini | 1.3회 | 3.6초 | 별도 rate limit / 비용 기준 적용 (약 $0.004/편) |

해석 기준(호출 ≤ 3회, 응답 시간 ≤ 10초) 충족 여부: **모두 충족**

### 6.5 정성적 사례 분석

**사례 1 (NER 오류가 검색에 큰 영향을 주지 않은 경우)** — "HBM4 적층 구조 설명"
검색. gemma2-9b는 STT 토큰화 오류로 "HBM4"를 개체명 "HBM"과 "4"로 분리 인식해
NER 채점상 오류로 처리되었다. 그러나 키워드 필드에는 "적층", "메모리", "HBM4"가
정확히 추출되어 있어 조건 C 인덱스에서도 정상적으로 상위 순위에 노출되었다
(Δrank 조건 A 대비 +6). 즉 개체명 필드의 국소적 오류가 반드시 검색 실패로
이어지지는 않았다.

**사례 2 (의료 도메인 개체명 오류가 실제로 검색에 영향을 준 경우)** — "다한증
보톡스 시술 후기" 검색. STT가 "보톡스"를 "보독스"로 오인식해 개체명·키워드 모두에서
누락되었고, 요약 필드도 시술명을 명시하지 못한 채 뭉뚱그려 서술되었다. 이 영상은
조건 B/C 모두에서 쿼리 "보톡스 시술 후기 영상"에 대해 상위 10위 밖으로 밀려났다
(Recall 실패 사례). 사례 1과 달리, 요약 단계에서부터 핵심 용어가 아예 누락되면
개체명 필드만으로는 만회되지 않는다는 것을 보여준다.

이 두 사례는 §6.3에서 관찰된 "NER F1은 낮지만 전체 검색 향상은 유의함"이라는
결과를 설명한다 — 개체명 인식 오류가 항상 검색 실패로 이어지는 것은 아니며, 요약·
키워드 단계에서 핵심 용어가 보존되는 한 개체명 필드의 국소적 오류는 상당 부분
흡수된다.

## 7. 논의

**메타데이터 품질과 검색 기여도의 괴리** — 가장 흥미로운 결과는 NER F1(특히 의료
도메인 0.48)이 상대적으로 낮음에도 불구하고 조건 C의 전체 검색 성능 향상(Δ
NDCG@5 = 0.078)이 해석 기준을 충족했다는 점이다. §6.3의 조건별 증분 분해에서
드러나듯, 향상의 대부분(0.053/0.078 ≈ 68%)은 이미 조건 B(요약+키워드)에서
발생했고 개체명·콘텐츠 유형이 추가된 조건 C의 증분 기여는 작지만 유의했다(0.025).
이는 "메타데이터 필드 하나하나가 개별적으로 고품질이어야 한다"는 가정이 항상
성립하지는 않으며, 벡터 검색이 요약·키워드 수준에서 이미 상당한 의미 정보를
포착한다면 개체명 필드의 정밀도가 다소 낮아도 전체 파이프라인의 실익은 유지될 수
있음을 시사한다. §6.5의 사례 1과 2는 이 차이를 구체적으로 보여준다 — 개체명
오류가 요약·키워드에서 핵심 용어가 보존된 채로 발생하면(사례 1) 검색에 미치는
영향이 제한적이지만, 요약 단계에서부터 핵심 용어가 누락되면(사례 2) 개체명
필드만으로는 만회되지 않는다.

**llama-3.1-8b와 gemma2-9b의 실용 기준 갈림길** — 두 모델은 파라미터 수(8B vs
9B)와 아키텍처 계열이 다르며, 본 실험에서는 gemma2-9b만 인간 평가 실용 기준
(3.5/5.0)을 충족했다(3.7 vs 3.4). 두 값의 차이(0.3점)가 통계적으로 유의한
수준인지는 본 연구의 평가자 규모(2인)로는 확정하기 어렵지만, 실무적으로는
Groq 무료 티어에서 "어떤 모델을 기본값으로 쓸 것인가"를 결정하는 데 직접적인
근거가 된다 — 단일 파라미터 규모만으로 실용성 여부를 예단할 수 없으며 실측이
필요하다는 점을 재확인한다.

**의료 도메인의 구조적 취약점** — 의료 도메인의 NER F1(0.48)은 기술(0.71)·
뉴스(0.69) 대비 뚜렷이 낮다. 원인은 모델의 추론 능력 부족이라기보다 STT 단계의
전문 용어 오인식(사례 2)에 가깝다. 이는 LLM 프롬프트 개선만으로는 해결되지 않는
문제이며, 의료 도메인에 특화된 STT 후처리(용어 사전 기반 보정 등)가 별도로
필요함을 시사한다.

## 8. 한계

- 인간 레퍼런스 및 Query-Relevance 쌍 구축이 가장 큰 병목이며, 평가자 2인 규모로는
  통계적 검정력에 한계가 있다 — 특히 llama-3.1-8b와 gemma2-9b의 인간 평가 차이
  (3.4 vs 3.7)가 통계적으로 유의한지는 별도 검정을 수행하지 않았다
- Groq API rate limit(14,400 req/day) 하에서의 측정으로, 상용 유료 티어나 온프레미스
  배포 환경의 처리량과는 다를 수 있다
- 개체명 인식 레이블은 인간 평가자의 주관적 판단에 의존하며, 전문 용어(의료·기술)
  경계 판단에 평가자 간 불일치가 존재할 수 있다
- 검색 평가는 gemma2-9b 출력만으로 수행했다 — llama-3.1-8b 출력을 조건 B/C에 썼을
  때도 동일한 정도의 검색 향상이 나타나는지는 확인하지 않았다
- Query-Relevance 쌍 50개는 기술 도메인에 다소 편중되었을 가능성이 있으며, 의료
  도메인 검색 성능은 별도로 세분화해 평가하지 않았다

## 9. 결론

본 연구는 STT 노이즈가 심한 한국어 YouTube 트랜스크립트에서 공개 LLM으로 요약·
키워드·개체명·콘텐츠 유형을 추출하는 파이프라인을 제안하고, 이를 추가했을 때
API 메타데이터 단독 대비 검색 정확도가 통계적으로 유의하게 향상됨을 확인했다
(NDCG@5 Δ=0.078, *p*=0.012). 무료 Groq 모델 중 gemma2-9b는 인간 평가 실용
기준을 충족했으나 llama-3.1-8b는 근소하게 미달해, 파라미터 규모만으로 실용성을
예단할 수 없음을 보였다. 개체명 인식 품질(특히 의료 도메인)은 상대적으로 낮았지만
검색 성능 향상의 상당 부분은 이미 요약·키워드 단계에서 발생했으며, 이는 메타데이터
필드별 품질과 하위 응용(검색) 기여도가 반드시 일치하지 않는다는 점을 실증한다.

향후 연구로는 (1) 영상 썸네일 비전 결합 멀티모달 메타데이터로의 확장, (2)
트랜스크립트 변경 감지 시 자동 재생성 파이프라인 구축, (3) 의료 도메인 특화 STT
후처리(전문 용어 사전 기반 보정)를 통한 개체명 인식 품질 개선을 고려할 수 있다.
